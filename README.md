# ระบบวางบิล Outsource อัตโนมัติ (OBS)

อ่าน Timesheet ของพนักงาน Outsource → ตรวจ Manday → สร้าง **Draft Invoice** ใน FlowAccount → ร่างอีเมลวางบิล

ลูกค้านำร่อง: บริษัท ไทยประกันชีวิต จำกัด (มหาชน) — โครงการ Outsource for BAU Project (ใบว่าจ้าง 26/B0113)

> **ตอนนี้ตั้งเป็นโหมด Manual** — คนอัปโหลดไฟล์เอง ตรวจเอง กดอนุมัติเอง ส่งเมลเอง
> รายละเอียดว่าต่างจากโหมด Auto ตรงไหน ดู [docs/manual-vs-auto.md](docs/manual-vs-auto.md)

---

## เริ่มใช้งาน

```bash
npm install
cp .env.example .env      # แก้ค่าตามต้องการ (รันได้เลยโดยไม่ต้องแก้)
npm run seed              # ใส่ข้อมูลจากเอกสารจริงรอบ ม.ค. 2026
npm run user:create       # สร้างบัญชี login ครั้งแรก — ไม่มีบัญชีเลยเปิดเว็บไม่ได้ (ดูหัวข้อ "เข้าสู่ระบบ")
npm start                 # เปิด http://localhost:4300
npm test                  # ทดสอบ core logic กับตัวเลขในใบแจ้งหนี้จริง
```

ต้องใช้ **Node 22.5 ขึ้นไป** (ใช้ `node:sqlite` ที่มาพร้อม Node) มี dependency เดียวคือ
`pdf-to-img` (แปลง Timesheet PDF เป็นรูปก่อนส่งให้โมเดล vision) — AI ทั้งหมดเรียกโมเดลที่รันในเครื่อง
ผ่าน LM Studio/Ollama ไม่ต้องมี API key หรือพึ่งบริการ AI ภายนอกเลย

คำสั่งอื่น
```bash
npm run reset             # ล้างฐานข้อมูลแล้วใส่ข้อมูลใหม่
npm run dev               # รันแบบ auto-reload
npm run user:create       # เพิ่มบัญชี login คนใหม่ — ระบุ role ได้ (admin/operator)
```

## เข้าสู่ระบบ

หน้าเว็บทุกหน้าต้อง login ก่อนใช้งาน — เก็บรหัสผ่านเอง (scrypt) ยังไม่ผูก SSO ของบริษัท
สร้างบัญชีด้วย `npm run user:create` (ถามทีละคำ หรือใส่ค่าตรงในคำสั่งเดียวก็ได้ ดูใน
`scripts/create-user.js`) มี 2 role:

| Role | ทำอะไรได้ |
|---|---|
| `admin` | ทำได้ทุกอย่าง รวมถึงแก้ข้อมูลหลัก (เรทพนักงาน สัญญา ชื่อพ้อง วันหยุด) |
| `operator` | งานประจำวันได้หมด (อัปโหลด Timesheet, ตรวจ Manday, อนุมัติวางบิล, ร่างอีเมล) แต่แก้ข้อมูลหลักไม่ได้ |

n8n และ LINE webhook ไม่ต้อง login — ยืนยันตัวด้วยวิธีของตัวเอง (n8n ยิงตรงไม่มี cookie,
LINE ตรวจลายเซ็น HMAC + รายชื่อ `LINE_APPROVER_USER_IDS`) รายละเอียดดู `src/auth.js`

## หน้าจอในระบบ — 6 หน้า

| เมนู | คนทำอะไรที่นี่ |
|---|---|
| **แดชบอร์ด** (หน้าแรก) | ภาพรวม — งานค้างแต่ละขั้น · กราฟมูลค่ารายเดือน · สถานะรอบบิลทั้งสัญญา · งานที่ต้องทำพร้อมปุ่มกดเข้าไปทำต่อ |
| **1 · อัปโหลด Timesheet** | ลากไฟล์ PDF มาวาง → กดให้ AI อ่าน → ตรวจ/แก้สิ่งที่อ่านได้ → กดยืนยันบันทึก · แท็บ "กรอกเอง" ไว้ใช้ตอนไฟล์อ่านไม่ออก |
| **2 · ตรวจ Manday** | การ์ด Timesheet พร้อมตารางคำนวณย่อ · ตัวกรอง 5 หมวด · ค้นหา · เปิดตรวจแล้ว **กดยืนยันว่าตรวจแล้ว** หรือตีกลับ |
| **3 · วางบิล & ร่างอีเมล** | รอบบิลทุกเดือนตามสัญญา · เปิดรอบแล้วเห็นใบแจ้งหนี้จำลองกับ payload → กดอนุมัติสร้างร่างใน FlowAccount → ให้ AI ร่างอีเมล → คัดลอกไปส่ง → บันทึกว่าส่งแล้ว |
| **ใบแจ้งหนี้** | ทะเบียนเอกสารที่สร้างเข้า FlowAccount — กางยอด VAT / หัก ณ ที่จ่าย ของทุกรอบไว้เทียบกันในตารางเดียว |
| **ข้อมูลหลัก** | พนักงาน+ชื่อพ้อง · ลูกค้า&สัญญา · วันหยุด+การเชื่อมต่อ — เข้ามาแก้เมื่อขั้น 2 บอกว่าจับคู่ไม่ได้หรือเรทไม่ตรง |

ป้ายเลขแดงบนเมนูขั้น 2 และ 3 บอกจำนวนงานค้างของขั้นนั้น ขึ้นเองผ่าน SSE ไม่ต้องกดรีเฟรช
เมนูข้างย่อเหลือแต่ไอคอนได้ด้วยปุ่ม "ย่อเมนู" ท้ายเมนู (จำสถานะไว้ให้) — คืนพื้นที่ให้เนื้อหา 192px
แถบบนบอก 2 อย่าง: โหมด FlowAccount (dry-run/sandbox/live) และโหมดระบบ (Manual/Auto)

## สิ่งที่ระบบทำ (4 ขั้น)

| ขั้น | หน้าที่ | ไฟล์ |
|---|---|---|
| 1 | อ่านอีเมลแจ้งอนุมัติ + ดึงไฟล์ Timesheet มาอ่านด้วยโมเดล vision ในเครื่อง | `src/extract/timesheet.js` |
| 2 | ตรวจและคำนวณ Manday เทียบปฏิทินวันหยุด | `src/domain/manday.js`, `src/domain/calendar.js` |
| 3 | ประกอบใบแจ้งหนี้และส่งเข้า FlowAccount **เป็นร่างเท่านั้น** | `src/domain/invoice.js`, `src/integrations/flowaccount.js` |
| 4 | ร่างอีเมลวางบิล — ระบบไม่ส่งเอง | `src/service.js` → `buildEmailDraft()` |

**ระบบหยุดรอคนอนุมัติที่ขั้น 3 ทุกครั้ง** และไม่ส่งอีเมลออกเอง
การเซ็นเอกสารและการกดส่งยังเป็นงานของเจ้าหน้าที่

## กฎการคิดเงิน

โมเดลคือ **เรทรายเดือนเต็มจำนวน หักส่วนลดวันลา** ไม่ใช่ `Manday × เรทรายวัน`
ยืนยันจากใบแจ้งหนี้จริง INV2026020006 ซึ่งลง `qty = 1 Months`, `unit price = เรทเดือน`, `discount = ค่าลา`

```
วันทำงานมาตรฐานของเดือน = วันจันทร์–ศุกร์ − วันหยุดที่ตรงวันทำงาน
อัตราต่อวัน              = เรทเดือน ÷ ตัวหาร            (ตัวหารตั้งในสัญญา ปัจจุบัน 20)
ส่วนลด                   = จำนวนวันลา × อัตราต่อวัน
ยอดของรายการ            = เรทเดือน − ส่วนลด

รวมเป็นเงิน        = ผลรวมเรทเดือนทุกคน
รวมหลังหักส่วนลด   = รวมเป็นเงิน − ส่วนลดรวม
VAT 7%            = รวมหลังหักส่วนลด × 7%
รวมทั้งสิ้น        = รวมหลังหักส่วนลด + VAT
หัก ณ ที่จ่าย 3%   = รวมหลังหักส่วนลด × 3%    ← คิดจากยอดก่อน VAT ไม่ใช่จากยอดรวมทั้งสิ้น
ยอดรับชำระ        = รวมทั้งสิ้น − หัก ณ ที่จ่าย
```

ตรวจแล้วว่าตรงกับใบจริงทุกบรรทัด:

| รายการ | ค่าในใบจริง |
|---|---|
| รวมเป็นเงิน | 176,363.93 |
| ส่วนลด (ลา 1 วัน) | 2,647.20 |
| รวมหลังหักส่วนลด | 173,716.73 |
| VAT 7% | 12,160.17 |
| รวมทั้งสิ้น | 185,876.90 |
| หัก ณ ที่จ่าย 3% | 5,211.50 |
| ยอดรับชำระ | 180,665.40 |

## ⚠️ เรื่องที่ต้องเคลียร์ก่อนใช้กับของจริง

### 1. ตัวหารอัตราต่อวันยังยืนยันไม่ได้
เดือน ม.ค. 2026 มีวันทำงาน 20 วันพอดี ทำให้ "หารด้วย 20 คงที่" และ "หารด้วยวันทำงานจริง"
ให้ผลเท่ากัน จึงยังแยกไม่ออกว่าสัญญาใช้แบบไหน — **ต้องขอใบแจ้งหนี้อีกเดือนที่วันทำงานไม่ใช่ 20
มาเทียบ** ระบบรองรับทั้งสองแบบแล้ว (ตั้งที่ `contracts.divisor_mode`) และจะเตือนทุกครั้งที่ยังแยกไม่ออก

### 2. ชื่อฟิลด์ของ FlowAccount API
`src/integrations/flowaccount.js` → `FIELD_MAP` เป็นโครงร่างที่ตั้งจากรูปแบบเอกสารจริง
**ยังไม่ได้เทียบกับ Postman Collection ทีละฟิลด์** ก่อนเปลี่ยนโหมดจาก `dry-run`:

1. import Postman Collection ที่ได้จาก FlowAccount
2. เทียบชื่อฟิลด์ใน `FIELD_MAP` กับ request body จริง
3. ยืนยันว่าจะใช้ Billing Note หรือ Tax Invoice ให้ตรง flow ฝ่ายบัญชี
4. ยืนยันว่า FlowAccount คิดภาษีหัก ณ ที่จ่ายให้เอง หรือเราต้องส่งไปด้วย

### 3. ปฏิทินวันหยุด
1–2 ม.ค. 2026 ยืนยันจาก Timesheet จริงแล้ว ที่เหลือใส่ตามวันหยุดราชการทั่วไป
**ต้องยืนยันกับปฏิทินบริษัทลูกค้า** เพราะกระทบวันทำงานมาตรฐานโดยตรง

### 4. เงื่อนไขประเภทการลา
ตอนนี้หักเงินทุกประเภทเท่ากัน ยังไม่ยืนยันว่าลาป่วย ลากิจ และลาพักร้อน
หักเหมือนกันหมดตามสัญญาหรือไม่

### 5. ช่อง Reference
ใบแจ้งหนี้ตัวจริงเว้นช่อง Reference ว่างไว้ (เอกสารออกแบบระบุว่าควรใส่เลข QT)
ระบบตอนนี้ทำตามใบจริงคือส่ง `null` — ต้องยืนยันว่าจะกรอกหรือปล่อยว่าง

## ต่อ Gmail (ไม่บังคับ)

ต่อแล้วได้ 2 อย่าง — **ขั้น 1** ดึงอีเมลแจ้งอนุมัติ + ไฟล์แนบเข้าระบบโดยไม่ต้องโหลดไฟล์เอง
และ **ขั้น 4** วางร่างอีเมลวางบิลไว้ในกล่อง Drafts

```bash
npm run gmail:auth
```

สคริปต์จะพิมพ์ลิงก์ให้เปิดในเบราว์เซอร์ กดยินยอมด้วยบัญชี Google ที่จะใช้ แล้วได้
`GMAIL_REFRESH_TOKEN` มาใส่ใน `.env` (ต้องมี `GMAIL_CLIENT_ID` / `GMAIL_CLIENT_SECRET`
จาก Google Cloud Console ก่อน — ขั้นตอนครบอยู่ในหน้า "อัปโหลด Timesheet" แท็บ "ดึงจาก Gmail")

> **ระบบไม่มีโค้ดส่งอีเมลเลย** — `src/integrations/gmail.js` ไม่เรียก `messages/send`
> แม้แต่ครั้งเดียว สร้างได้แค่ร่าง คนเป็นคนกดส่งเอง
> (Google ไม่มี scope ที่ให้ "สร้างร่างได้แต่ส่งไม่ได้" หลักประกันจึงอยู่ที่ตัวโค้ด ไม่ใช่ที่ scope)

## ทางเลือกออกแบบที่ตัดสินใจไว้

**ทำไมไม่ใช้ n8n** — เอกสารออกแบบเดิมวางไว้เป็น n8n + LLM โปรเจคนี้ทำเป็นแอปแทน
เพราะ logic คำนวณเงินต้องมี unit test ที่ยืนยันกับใบจริงได้ ซึ่งทำใน n8n ไม่สะดวก
ถ้าสุดท้ายจะใช้ n8n เป็น orchestrator ก็เรียก API ของระบบนี้ได้ทันที (`/api/timesheets/ingest`,
`/api/cycles/ready`, `/api/cycles/.../approve`) โดยไม่ต้องย้าย logic — ซึ่งตอนนี้ n8n ทำอยู่แล้ว

**ทำไมไม่มี dependency** — ใช้ `node:sqlite`, `node:http`, `node:test` ที่มาพร้อม Node
ทีมไม่ต้องติดตั้งอะไรและไม่มี native module ที่ต้อง compile

**ทำไมมีโหมด dry-run** — ทำให้ทดสอบ flow ได้ครบตั้งแต่วันแรกโดยไม่ต้องรอ credential ของ FlowAccount
และป้องกันการยิงเอกสารจริงโดยไม่ตั้งใจ
