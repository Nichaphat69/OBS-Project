## 1. ระบบนี้คืออะไร

**Outsource Billing System (OBS)** เป็นเครื่องมือภายในฝ่ายบัญชีของ iPassion Co., Ltd.
สำหรับวางบิลค่าจ้างพนักงาน Outsource ที่ไปประจำอยู่ที่ออฟฟิศลูกค้า

ระบบรับช่วงงานเอกสารตั้งแต่**อีเมลแจ้งอนุมัติ Timesheet เข้ามา** จนถึง**ร่างใบแจ้งหนี้และร่างอีเมลวางไว้ให้**
เหลือให้คนทำเพียง **ตรวจ · กดอนุมัติ · เซ็น · กดส่ง**

หลักการที่คุมทั้งระบบ:
> ระบบเตรียมเอกสารให้เสร็จ แต่ไม่ตัดสินใจแทนคน — ทุกใบยังต้องมีคนตรวจและกดเอง

**ลูกค้าที่ใช้ตั้งต้นระบบ** — บริษัท ไทยประกันชีวิต จำกัด (มหาชน)
สัญญา จซ.002/2569 · ใบว่าจ้าง 26/B0113 · โครงการ Outsource for BAU Project · พนักงาน 2 คน · 6 เดือน

ระบบออกแบบให้รองรับหลายลูกค้าและหลายสัญญา ไม่ได้ผูกกับไทยประกันชีวิตรายเดียว

## 3. ตรรกะการคิดเงิน

### สัญญานี้คิดแบบเหมาเดือน ไม่ใช่นับวัน

จุดที่เข้าใจผิดกันบ่อยที่สุด — **ไม่ใช่** `จำนวนวันที่มาทำงาน × อัตราต่อวัน`

```
ยอดของพนักงาน 1 คน = เรทรายเดือนเต็มจำนวน − (จำนวนวันลา × อัตราต่อวัน)
```

ในใบแจ้งหนี้ ช่องจำนวนจะเป็น **`1 Months` เสมอ** และวันลาไปโผล่ในช่อง**ส่วนลด** ไม่ได้ไปลดจำนวนวัน

```
อัตราต่อวัน = เรทรายเดือน ÷ จำนวนวันทำงานมาตรฐานของเดือนนั้น
```

### ลำดับการคิดภาษี

ลำดับนี้ตรวจตรงกับใบแจ้งหนี้ INV2026020006 ทุกบรรทัด และมีชุดทดสอบคุมไว้

## 4. การตรวจสอบความถูกต้อง

`src/domain/manday.js` ตรวจ **5 เรื่อง แตกเป็น 8 เงื่อนไข** ผลออกมา 3 ระดับ

| ระดับ | ความหมาย |
|---|---|
| `pass` ผ่าน | ไปต่อได้ |
| `warn` เตือน | ไปต่อได้ แต่ให้คนอ่านก่อน |
| `fail` ไม่ผ่าน | **กดอนุมัติไม่ได้** จนกว่าจะแก้ |

| เรื่องที่ตรวจ | รหัส | ระดับ | เงื่อนไข |
|---|---|---|---|
| 1. ผลรวมวันตรงกับปฏิทิน | `workday_sum` | pass / **fail** | วันทำงานที่รายงาน + วันลา ต้องเท่ากับวันทำงานของเดือน |
| 2. วันลาอยู่ในรอบบิล | `leave_out_of_period` | **fail** | วันลาที่ระบุมาไม่ได้อยู่ในเดือนนั้น |
| 2. วันลาไม่ตรงเสาร์–อาทิตย์ | `leave_on_weekend` | **fail** | ลาในวันที่ไม่ใช่วันทำงาน = กรอกผิด ไม่ควรหักเงิน |
| 2. วันลาไม่ตรงวันหยุด | `leave_on_holiday` | **fail** | เหตุผลเดียวกัน |
| 3. ป้ายกำกับตรงกับปฏิทิน | `label_mismatch` | warn | Timesheet เขียน "Holiday" ในวันเสาร์–อาทิตย์ · ไม่กระทบยอดเงิน |
| 4. ตัวหารยืนยันได้ | `divisor_ambiguous` | warn | เดือนนั้นวันทำงานเท่ากับตัวหารคงที่พอดี แยกไม่ออกว่าใช้แบบไหน |
| 4. ตัวหารตรงกับความจริง | `divisor_differs` | warn | ใช้ตัวหารคงที่ แต่เดือนนั้นวันทำงานจริงไม่เท่า |
| 5. วันที่คิดเงินไม่ติดลบ | `payable_negative` | **fail** | วันลามากกว่าวันทำงานมาตรฐาน = ข้อมูลผิด |

**ข้อสำคัญ** — มีแค่ `workday_sum` ที่ขึ้นรายการทั้งตอนผ่านและไม่ผ่าน
ข้ออื่นจะ**โผล่มาเฉพาะเมื่อมีปัญหา** ถ้าไม่มีปัญหาก็ไม่มีรายการนั้นเลย
เพราะฉะนั้นเวลาเห็น "ผ่าน 1 · ทักไว้ 1 · ไม่ผ่าน 0" คือปกติ ไม่ได้แปลว่าตรวจไม่ครบ

## 9. การทำงานอัตโนมัติด้วย n8n

**n8n รับหน้าที่จุดชนวนและตั้งเวลา · OBS รับหน้าที่คิดเงิน**

กฎการคิดเงินทั้งหมดอยู่ใน OBS และมีชุดทดสอบคุม n8n ไม่ต้องรู้กฎเลย แค่ส่งไฟล์เข้ามาแล้วอ่าน `nextAction`
ถ้าวันหลังเปลี่ยนจาก n8n ไปใช้อย่างอื่น ตัวคิดเงินไม่ต้องแก้

| Workflow | หน้าที่ |
|---|---|
| `n8n/01-obs-workflow.json` | ไฟล์เดียว 2 trigger (รวมเป็นไฟล์เดียว 4 ส.ค. 69 เพื่อกด Activate ที่เดียว) — **Gmail Trigger** (poll 30 นาที) → IF สถานะ "อนุมัติ" → Code ดึงเลขเอกสาร + แปลงไฟล์เป็น base64 → `POST /ingest` → Switch ตาม `nextAction` แตก 3 ทาง · **Schedule Trigger** ทุกวันทำการ 09:00 → `GET /cycles/ready` → splitOut → IF `canApprove` → `POST /request-approval` (ส่งเข้า LINE ให้คนกดก่อน ไม่เรียก `/approve` ตรงอีกต่อไป) |

URL ของ OBS เขียนตรงไว้ในโหนดแล้ว (`http://localhost:4300`) แก้เองถ้าเครื่องรัน n8n คนละเครื่องกับ OBS
ยังต้องผูก credential Gmail เอง — รายละเอียดอยู่ใน [`n8n/README.md`](../n8n/README.md)

> ⚠️ พารามิเตอร์ของ node ใน JSON เป็นแบบ best-effort อาจต้องปรับในหน้า n8n เพราะรูปแบบต่างกันตามเวอร์ชัน
> โครง workflow กับ HTTP call ถูกต้อง แต่ควรกด Execute ทีละ node ดูครั้งแรก

## 11. การเชื่อมต่อ FlowAccount

`src/integrations/flowaccount.js` — มี 3 โหมด

| โหมด | ทำอะไร |
|---|---|
| `dry-run` | **โหมดปัจจุบัน** — คำนวณและเตรียม payload ครบ แต่**ไม่เรียก API เลย** ไม่มีเอกสารเกิดขึ้น จำลองเลขที่เอกสารให้ดู |
| `sandbox` | ยิงเข้าสภาพแวดล้อมทดสอบของ FlowAccount |
| `live` | ยิงของจริง |

**ระบบสร้างเป็นร่าง (Draft) เท่านั้น** การกดอนุมัติเอกสารในระบบบัญชียังเป็นงานคน

> ⚠️ `FIELD_MAP` ในไฟล์นี้ตั้งจากรูปแบบเอกสารจริง **ยังไม่ได้เทียบกับเอกสาร API ทีละฟิลด์**
> ถ้าเปลี่ยนออกจาก dry-run เลยโดยไม่เทียบก่อน เอกสารจะสร้างไม่สำเร็จ

## 12. สิ่งที่ระบบไม่ทำ — ตั้งใจให้เป็นแบบนี้

ไม่ใช่ข้อจำกัด แต่เป็นเส้นที่ตกลงกันไว้ว่าคนต้องเป็นคนตัดสินใจ

| ระบบไม่ทำ | เหตุผล |
|---|---|
| ไม่ออกเอกสารตัวจริง | สร้างเป็นร่างใน FlowAccount เท่านั้น |
| **ไม่ส่งอีเมลเอง** | ร่างหัวเรื่องและเนื้อความไว้ให้ คนอ่านทวนแล้วกดส่ง |
| ไม่เซ็นเอกสาร | ลายเซ็นและตราประทับเป็นงานคน รวมถึงการนำเอกสารไปวางบิลที่อาคารลูกค้า |
| ไม่ข้ามข้อที่ตรวจไม่ผ่าน | มี `fail` ค้างอยู่ = ปุ่มอนุมัติถูก disable และ API คืน `409` |
| ไม่เดาเมื่อจับคู่ชื่อไม่ได้ | ไม่บันทึกเลย แจ้งให้คนไปเพิ่มชื่อพ้องก่อน |
| ไม่บันทึกการรับเงิน | สถานะชำระจริงอยู่ที่ FlowAccount ระบบนี้ไม่ติดตามลูกหนี้ (เอาออกแล้วเพราะเกินขอบเขต — ดู `scope-audit.md`) |

## 13. เรื่องที่ต้องเคลียร์ก่อนใช้กับของจริง

ทุกข้อเป็นข้อมูลที่ต้องยืนยันจากคนหรือจากลูกค้า **ไม่ใช่งานเขียนโค้ด**

| # | เรื่อง | รายละเอียด |
|---|---|---|
| 1 | **ตัวหารอัตราต่อวัน** | ม.ค. 2569 มีวันทำงาน 20 วันพอดี ทำให้ "หาร 20 คงที่" กับ "หารด้วยวันทำงานจริง" ให้ผลเท่ากัน จึงยังแยกไม่ออก — **ต้องขอใบแจ้งหนี้อีกเดือนที่วันทำงานไม่ใช่ 20 วันมาเทียบ** ระบบรองรับทั้งสองแบบแล้ว (`contracts.divisor_mode`) และเตือนทุกครั้งที่แยกไม่ออก |
| 2 | ~~ชื่อฟิลด์ FlowAccount API~~ | **เคลียร์แล้ว 29 ก.ค. 2569** — เทียบกับ Postman Collection ตัวจริงครบทุกฟิลด์ ดูข้อ 2.1–2.3 ที่แตกออกมา |
| 2.1 | **`items[].id`** | ตัวอย่างใน Collection กำกับว่า *"use existing product list id"* ยังไม่รู้ว่าจำเป็นจริงหรือไม่ ถ้าจำเป็นต้องสร้างรายการบริการไว้ก่อนด้วย `/product-masters` — **ต้องยิง sandbox ทดสอบ** |
| 2.2 | **รหัสผังบัญชีค่าบริการ** | ใช้ `41210` ตามตัวอย่างใน Collection ต้องให้ฝ่ายบัญชียืนยันว่าตรงกับผังบัญชีจริงของ iPassion |
| 2.3 | **Billing Note หรือ Tax Invoice** | ยังต้องเลือกให้ตรง flow บัญชีปัจจุบัน ทั้งสองตัวมี endpoint `inline` เหมือนกัน สลับได้ด้วย `documentType` |
| 3 | **ปฏิทินวันหยุด** | ยืนยันได้แค่ 1–2 ม.ค. 2569 จาก Timesheet จริง ที่เหลือใส่ตามวันหยุดราชการทั่วไป — ต้องขอปฏิทินของบริษัทลูกค้า เพราะกระทบวันทำงานมาตรฐานโดยตรง |
| 4 | **เงื่อนไขประเภทการลา** | ตอนนี้หักเงิน**ทุกประเภทเท่ากันหมด** รวมลาพักร้อน ยังไม่ยืนยันว่าถูกตามสัญญาหรือไม่ |
| 5 | **ช่อง Reference** | ใบจริงเว้นว่างไว้ แต่เอกสารออกแบบระบุว่าควรใส่เลขใบเสนอราคา — ต้องเลือกอย่างใดอย่างหนึ่ง ระบบตอนนี้ทำตามใบจริงคือส่ง `null` |

### สิ่งที่ได้คำตอบจากการเทียบ Postman Collection (29 ก.ค. 2569)

ที่มา: `OpenAPI - Collection` → `Tax Invoices (INV)` → `Create-INV-Inline`

| ประเด็น | คำตอบ |
|---|---|
| **ต้องใช้ endpoint ตัวไหน** | `POST /tax-invoices/inline` — **ไม่ใช่** `/tax-invoices` เฉยๆ เพราะตัวธรรมดามีแต่ส่วนลดระดับเอกสาร ขณะที่โมเดลคิดเงินของเราหักส่วนลดวันลา**รายบรรทัด** |
| **เปิดส่วนลดรายบรรทัดยังไง** | ต้องส่งครบสามตัวพร้อมกัน — `documentStructureType: 'InlineDocument'` · `useInlineDiscount: true` · `discountType: 1` |
| **ภาษีหัก ณ ที่จ่าย** | **เราต้องคิดแล้วส่งไปเอง** ผ่าน `documentWithholdingTaxPercentage` + `documentWithholdingTaxAmount` FlowAccount ไม่คิดให้ |
| **สร้างเป็นร่างยังไง** | **ไม่มีฟิลด์ `status` ในสเปก** — เอกสารที่ POST เข้าไปเป็นร่างอยู่แล้ว การอนุมัติเป็น endpoint แยก `POST /{doc}/{id}/status/awaiting` ซึ่งระบบนี้ไม่มีโค้ดเรียกเลย นั่นคือที่มาของหลักประกัน "ร่างเท่านั้น" |
| **ขอ token** | `POST {base}/token` เป็น `x-www-form-urlencoded` (ไม่ใช่ JSON) · `scope = flowaccount-api` · sandbox base = `https://openapi.flowaccount.com/test` |
| **ชื่อฟิลด์ที่เดาผิด** | `documentDate` → **`publishedOn`** · `items[].discount` → **`items[].discountAmount`** · `vatType` → **`vatRate` รายบรรทัด + `vatAmount` ระดับเอกสาร** · `withholdingTaxOption` → **`documentWithholdingTaxAmount`** |
