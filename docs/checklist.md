## 5. ✅ แก้แล้ว 31 ก.ค. 69 — ประตูมนุษย์อยู่ผิดขั้น

n8n workflow ทั้งสองไฟล์เดิม**ยิงสร้างร่างเองโดยไม่มีคนมาเกี่ยวเลย**

```
01-ingest:  Gmail → IF อนุมัติ → ingest → switch → สร้างร่างใน FlowAccount     ← ไม่มีคน (ของเดิม)
02-daily:   ทุกวัน 09:00 → /cycles/ready → IF → สร้างร่างใน FlowAccount        ← ไม่มีคน (ของเดิม)
```

### ที่แก้ไปแล้ว
ทั้งสอง workflow เปลี่ยนไปเรียก **`POST /api/cycles/:id/:period/request-approval`** แทน `/approve`
ตรงๆ — endpoint นี้แค่ส่ง Flex Message สรุปรอบบิล (ลูกค้า โครงการ จำนวนคน ยอดรับชำระ) พร้อมปุ่ม
"อนุมัติ"/"ตีกลับ" เข้า LINE (`src/integrations/line.js`) **ยังไม่สร้างเอกสารใดๆ**

ร่างใน FlowAccount จะเกิดต่อเมื่อมีคนกดปุ่มใน LINE จริงๆ — OBS รับ webhook เองที่
`POST /api/line/webhook` (ตรวจลายเซ็น HMAC + ตรวจ `userId` อยู่ในรายชื่อ `LINE_APPROVER_USER_IDS`
ก่อนเชื่อ) แล้วเรียก `approveCycle()` ตัวเดิมให้ ดู `src/service.js` → `requestCycleApproval()` /
`decideCycleApproval()` / `processLineWebhook()` และเทสต์ใน `test/line-approval.test.js` (12 ข้อ)

### ทำไมรับ webhook ที่ OBS เอง ไม่ผ่าน n8n ตามที่วางแผนไว้เดิม
แผนเดิม (หัวข้อ 10 เวอร์ชันก่อนหน้า) จะให้ LINE ยิง webhook เข้า n8n ก่อน แล้ว n8n ค่อยเรียก OBS
แต่ OBS มีเซิร์ฟเวอร์ HTTP ของตัวเองอยู่แล้ว การรับตรงจึงตัดการเรียกซ้อนหนึ่งชั้น และไม่ต้องเขียน
ตรรกะตรวจลายเซ็น/ตรวจสิทธิ์ซ้ำสองที่ (n8n + OBS) — ยังไม่ได้ยิง end-to-end จริงเพราะยังไม่มี
LINE Developers channel ให้ทดสอบ (ต้องขอ credential จากคน ดูหัวข้อ 8)

### ปุ่มบนหน้าเว็บ "อนุมัติและสร้างร่างใน FlowAccount" ยังเรียก `/approve` ตรงเหมือนเดิม
คนนั่งกดจากเบราว์เซอร์เองก็เป็นประตูมนุษย์อยู่แล้ว (โหมด manual) — ประตู LINE ปิดเฉพาะทางที่ n8n

## 11. ✅ เพิ่มนอกเอกสาร 31 ก.ค. 69 — ระบบ login + role

เอกสารออกแบบเดิมไม่ได้พูดถึง auth เลย (ใช้ env `ACTOR` ตัวเดียวของทั้งเซิร์ฟเวอร์มาตลอด) แต่พอ
เปิดให้คนที่สองใช้เว็บพร้อมกัน `ACTOR` ตัวเดียวทำให้ audit log ผิดความจริงทันที — เพิ่มเข้ามาเพราะจำเป็น
ไม่ใช่ตัดสินใจทำเกินสเปกแบบหัวข้อ 6

**ทำอะไรไปแล้ว**
- `src/auth.js` — login ด้วยรหัสผ่านเก็บเอง (scrypt) + session cookie (HttpOnly) ยังไม่ผูก SSO
- ตาราง `users` / `sessions` ใน schema
- 2 role: `admin` (แก้ข้อมูลหลักได้) / `operator` (งานประจำวันได้แต่แก้ข้อมูลหลักไม่ได้)
- ทุก endpoint ต้อง login ยกเว้น `/auth/*`, `/timesheets/ingest`, `/cycles/ready`,
  `/cycles/.../request-approval`, `/line/webhook` (จุดที่ n8n/LINE เรียกตรง ไม่มี cookie)
- `npm run user:create` — สร้างบัญชีใหม่ (ถามทีละคำ หรือใส่ค่าตรงในคำสั่งเดียว)
- หน้า login เต็มจอ + ปุ่ม logout บนแถบบน + แสดง role ("ผู้ดูแลระบบ"/"พนักงานบัญชี") ข้างชื่อ
- เทสต์ 13 ข้อ (`test/auth.test.js`) + ทดสอบจริงผ่านเบราว์เซอร์ครบ (login/logout/403 ของ operator)

**ยังไม่ทำ**

## 12. ✅ เปลี่ยนแล้ว 3 ส.ค. 69 — เลิกใช้ Claude API ทั้งระบบ ย้ายไปโมเดลในเครื่อง

เอกสารออกแบบเดิม (ข้อ 1.4, 4.4) ระบุ Claude API ชัดเจน แต่ตัดสินใจไม่ใช้บริการ AI ภายนอกเลย —
ย้ายทั้งสองจุดไปเรียกโมเดลที่รันในเครื่องแทน (LM Studio/Ollama ผ่าน endpoint แบบ OpenAI-compatible)

**ทำอะไรไปแล้ว**
- ถอด `@anthropic-ai/sdk` ออกจาก dependency ทั้งหมด เพิ่ม `pdf-to-img` แทน (แปลง PDF → รูปภาพ
  ก่อนส่งให้โมเดล vision — ทดสอบแล้วว่าใช้งานได้จริงโดยไม่ต้องพึ่ง native lib เพิ่ม เช่น ImageMagick/Poppler)
- `src/llm/localClient.js` (ใหม่) — ตัวกลางเรียกโมเดลในเครื่อง ใช้ร่วมกันทั้งสองจุด บังคับคำตอบเป็น
  JSON ด้วย `response_format: {type: 'json_schema', json_schema: {strict: true, schema}}`
  (LM Studio ไม่รับ `json_object` — ทดสอบยิงตรงแล้วโดน 400 จึงแก้เป็น `json_schema` แบบ strict)
  แล้วตรวจคีย์ที่ต้องมีซ้ำด้วยโค้ดอีกชั้นเผื่อโมเดลตอบไม่ครบ
- `src/extract/timesheet.js` — อ่าน PDF ด้วยโมเดล **vision** (`LOCAL_LLM_VISION_MODEL`) แทน Claude
- `src/llm/email.js` — ร่าง/อ่านอีเมลด้วยโมเดล **ข้อความล้วน** (`LOCAL_LLM_MODEL`) แทน Claude
- เอา gate ตรวจ `ANTHROPIC_API_KEY` ออกจาก `server.js` ทุกจุด (local ไม่ต้องมี API key)
- อัปเดตหน้าตั้งค่าให้แสดงสถานะโมเดลในเครื่องแทน "Claude API"
- **3–4 ส.ค. 69 (เพิ่มหลังพบปัญหาจริง)** — เปลี่ยนจากส่งทั้งไฟล์ PDF หลายหน้า+schema ใหญ่ในคำขอเดียว
  (โมเดลปฏิเสธตอบ "I cannot fulfill this request" เมื่อรูปเกิน 3-4 หน้า) เป็น **อ่านทีละหน้า + รวมผล
  ด้วยโค้ด** (`mergePageResults()`) — หน้าที่อ่านไม่สำเร็จแค่บางหน้าไม่ทำให้ทั้งฉบับพัง เดาแบบ "ไม่เห็นค่านี้
  ในหน้านี้" ได้อย่างสุจริตเพราะ Timesheet จริงเป็น Excel export แยกหน้าซ้าย (ตาราง)/หน้าขวา (ชื่อ+เซ็น)
- เปลี่ยนโมเดลจาก `google/gemma-3-4b` เป็น **`google/gemma-4-e2b`** (ทั้ง `LOCAL_LLM_MODEL` และ
  `LOCAL_LLM_VISION_MODEL` — เครื่องนี้โหลดสองโมเดลพร้อมกันไม่ไหว จึงใช้ตัวเดียวกันทั้งสองงาน) แม่นกว่า
  แต่ช้ากว่าเดิมมาก (~4 นาที/ไฟล์)

**ทำไมถึงยอมรับ trade-off นี้**
- โมเดล vision ในเครื่องแม่นน้อยกว่า Claude ชัดเจนโดยเฉพาะกับ PDF สแกน/เอียง — ยอมรับความเสี่ยงนี้แล้ว
  เพราะ `verifyExtraction()` ยังตรวจซ้ำด้วยโค้ดเหมือนเดิมทุกจุด และคนยังต้องยืนยันก่อนบันทึกเสมอ
  (โหมด manual) — Gemma รุ่น 2B ธรรมดาเป็น text-only ทำ vision ไม่ได้เลย ต้องใช้รุ่นที่รองรับภาพ

**ยังต้องทำเอง**
- เปิด Local Server ใน LM Studio (หรือรัน Ollama) ให้พร้อมก่อนใช้งานทั้งสองฟีเจอร์เสมอ — ไม่มี
  fallback ไปที่บริการภายนอกแล้ว ถ้า local server ไม่รันจะ error ทันที (ข้อความบอกชัดว่าต้องเปิดอะไร)
- ตั้งชื่อโมเดลใน `.env` (`LOCAL_LLM_MODEL`, `LOCAL_LLM_VISION_MODEL`) ให้ตรงกับที่โหลดไว้จริงในเครื่อง
