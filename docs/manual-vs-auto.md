# โหมด Manual กับ Auto ต่างกันตรงไหน

> ปรับปรุง 31 กรกฎาคม 2569 · เขียนจากโค้ดจริงหลังปรับระบบเป็นโหมด Manual
> ระบบตอนนี้ตั้งเป็น **โหมด Manual** — ทุกขั้นมีคนกดเอง ไว้ใช้เดโมและใช้งานจริงชั่วคราว

---

## สรุปใน 1 บรรทัด

**กฎการคิดเงินและการตรวจเป็นชุดเดียวกันทั้งสองโหมด** ต่างกันแค่ **ใครเป็นคนกดปุ่ม**
โหมด Manual คนกด 4 จุด · โหมด Auto n8n กดแทน 2 จุดแรก เหลือคนกดจุดที่ 3–4

สลับโหมดด้วยค่าเดียว: `billing_rules.requireHumanCheck`

## จุดที่ใช้ LLM (Claude) — มี 2 จุด ไม่ควรมีมากกว่านี้

| จุด | ทำอะไร | ทำไมต้องเป็น LLM | กันพลาดยังไง |
|---|---|---|---|
| **1.1 อ่าน Timesheet PDF** | อ่านตาราง 28–31 แถว · ชื่อ · ตำแหน่ง · วันลา · ลายเซ็น | ไฟล์เป็น PDF export จาก Excel มีภาษาไทยผสม · text extraction ธรรมดาได้ตัวอักษรเพี้ยน | บังคับ JSON schema · `verifyExtraction()` ตรวจซ้ำด้วยโค้ด · คนดูก่อนบันทึก (โหมด Manual) |
| **4 ร่างอีเมล** | เรียบเรียงตัวเลขเป็นภาษาคน + อธิบายว่าเดือนนี้ต่างจากเดือนก่อนเพราะอะไร | template เขียนได้แค่สิ่งที่เดาไว้ล่วงหน้า เหตุผลที่ยอดต่างเปลี่ยนทุกเดือน | **ห้ามคิดเลขเอง** — ส่งเฉพาะตัวเลขที่คำนวณแล้วให้เรียบเรียง · ยังไม่ส่งออกจนคนกด |

**จุดที่จงใจไม่ใช้ LLM** — คิดเงิน · นับวันทำงาน · ตัดสินว่าผ่าน/ไม่ผ่าน · ประกอบ payload
ทั้งหมดเป็นโค้ดที่มีชุดทดสอบ 27 ข้อคุมไว้ ตรวจตรงกับใบแจ้งหนี้จริง INV2026020006 ทุกบรรทัด
เรื่องเงินให้โมเดลตัดสินไม่ได้ เพราะทวนย้อนกลับไม่ได้ว่าทำไมถึงได้ตัวเลขนั้น

## อีเมลถูกยิงตรงไหนบ้าง

| จุด | ทิศทาง | โหมด Manual | โหมด Auto |
|---|---|---|---|
| **ขาเข้า** — ลูกค้าแจ้งอนุมัติ Timesheet | ลูกค้า → เรา | คนเปิดเมลเอง โหลดไฟล์มาอัปโหลด | Gmail trigger ดึงเอง |
| **แจ้งเตือนทีมเมื่อตรวจไม่ผ่าน** | ระบบ → ทีม | ไม่มี — คนเห็นจากป้ายเลขบนเมนูขั้นที่ 2 | LINE Business (**ยังไม่ทำ**) |
| **ขาออก** — วางบิลถึงลูกค้า | เรา → ลูกค้า | **ระบบไม่ส่ง** · คัดลอกร่าง/เปิด mailto แล้วคนกดส่งเอง | สร้าง Gmail draft (**ยังไม่ทำ**) · **ยังไม่ auto-send เหมือนกัน** |

> **หลักที่ไม่เปลี่ยนทั้งสองโหมด** — ระบบไม่ส่งอีเมลออกหาลูกค้าเอง และไม่กดอนุมัติเอกสารใน FlowAccount เอง
> เอกสารที่สร้างเป็นร่างเสมอ (ในโค้ดไม่มีบรรทัดไหนเรียก endpoint อนุมัติของ FlowAccount เลย)

## หน้าจอในโหมด Manual — เหลือ 5 หน้า

เดิม 8 แท็บ ตัดเหลือ 5 ตามหลัก: **หน้านั้นเป็นขั้นตอนที่คนต้องลงมือทำหรือไม่**
บวกแดชบอร์ดอีกหน้าที่เก็บไว้เพราะใช้ดูภาพรวมได้ แม้ไม่ใช่ขั้นตอนงาน

| เมนู | คือขั้นไหน | คนทำอะไรที่นี่ |
|---|---|---|
| **แดชบอร์ด** | — (หน้าแรก) | ดูภาพรวม: เงินค้างอยู่ขั้นไหน · กราฟมูลค่ารายเดือน · สัดส่วนสถานะรอบบิล · **งานที่ต้องทำ** เรียงตามสิ่งที่กดต่อได้เลย · ความคืบหน้าสัญญา · ล่าสุดในระบบ |
| **1 · อัปโหลด Timesheet** | ขั้น 1 | ลากไฟล์มาวาง → ให้ AI อ่าน → ตรวจสิ่งที่อ่านได้ → กดยืนยันบันทึก · (มีแท็บ "กรอกเอง" ไว้ใช้ตอนไฟล์อ่านไม่ออก) |
| **2 · ตรวจ Manday** + หน้าตรวจ | ขั้น 2 | อ่านปฏิทินและผลตรวจ → **กดยืนยันว่าตรวจแล้ว** หรือ ตีกลับ |
| **3 · วางบิล & ร่างอีเมล** + หน้าอนุมัติ | ขั้น 3–4 | ดูใบแจ้งหนี้จำลอง → กดอนุมัติสร้างร่าง → ให้ AI ร่างอีเมล → คัดลอกไปส่ง → บันทึกว่าส่งแล้ว |
| **ข้อมูลหลัก** | ไม่ใช่ขั้นตอน | เข้ามาแก้เมื่อขั้น 2 บอกว่าจับคู่ชื่อไม่ได้ · เรทไม่ตรง · วันหยุดขาด |

ป้ายเลขแดงบนเมนูขั้น 2 และ 3 บอกว่ามีงานค้างกี่ชิ้นในขั้นนั้น — ขึ้นเองไม่ต้องกดรีเฟรช

## สวิตช์สลับโหมด

```
billing_rules.requireHumanCheck = true    ← ตอนนี้ (Manual)
```
* รอบบิลที่ครบทุกคนและตรวจผ่าน จะได้สถานะ **"รอคนตรวจ"** ไม่ใช่ "รออนุมัติ"
* `/cycles/ready` ไม่คืนรอบนั้น → n8n ตัวตั้งเวลาจะยังไม่แตะ
* `/approve` ตอบ 409 พร้อมบอกชื่อคนที่ยังไม่มีใครยืนยัน

```
billing_rules.requireHumanCheck = false   ← โหมด Auto
```
* ขั้น 1.2 กับ 2.1 หายไป ระบบไหลจาก `/ingest` → `/approve` เองได้
* คนยังต้องกดอนุมัติที่หน้ารอบบิลอยู่ดีถ้าไม่เปิด n8n ตัวตั้งเวลา

### ตราประทับ "คนตรวจแล้ว" หมดอายุเองได้

ตราไม่ได้ผูกกับใบ แต่ผูกกับ **ยอดชุดที่คนเห็นตอนกด** (`lineAmount` + `payableDays`)
ถ้ายอดเปลี่ยนหลังจากนั้น — ลูกค้าส่ง Timesheet ฉบับแก้มาทับ · มีคนเพิ่มวันหยุด · แก้เรท —
ตราจะกลายเป็น "ยอดเปลี่ยนหลังยืนยันไปแล้ว" และรอบบิลกลับไปติดที่ขั้น 2 อีกครั้ง
ไม่งั้นจะมีคนอนุมัติยอดที่ไม่เคยมีใครดู (มีชุดทดสอบคุมกรณีนี้ไว้)

## เพิ่มเติม 31 ก.ค. 2569 (รอบสาม) — ต่อ Gmail + เอา 2 หน้ากลับ

### ขั้นที่ 1 มี 3 ทางแล้ว

| ทาง | คนทำอะไร | ระบบทำอะไร | ใช้เมื่อ |
|---|---|---|---|
| **ดึงจาก Gmail** | กด "ดึงรายการเมล" → เลือกฉบับ → กด "ให้ AI อ่าน" | ดึงไฟล์แนบ + **อ่านเนื้อเมลด้วย LLM** → ได้เลขที่เอกสาร · สถานะ "อนุมัติ" · ผู้อนุมัติ · วันที่ | ต่อ Gmail แล้ว — ใกล้โหมด Auto ที่สุด |
| **อัปโหลดไฟล์** | ลากไฟล์ PDF มาวาง + พิมพ์เลขที่เอกสารเอง | AI อ่านเฉพาะไฟล์ | ไม่อยากต่อ Gmail |
| **กรอกเอง** | กรอก 6 ช่อง + วันลา | สร้างตารางรายวันจากปฏิทิน | ไม่มี API key หรือไฟล์อ่านไม่ออก |

ทั้งสามทางไปจบที่หน้าจอเดียวกัน — **ให้คนตรวจสิ่งที่อ่านได้แล้วกดยืนยัน** จึงบันทึก

**ตัวกันพลาดที่ได้มาจากการอ่านเนื้อเมล** (ทำในโค้ด ไม่ใช่ให้โมเดลตัดสิน)
- อีเมลไม่ได้เขียนว่า "อนุมัติ" → บันทึกไม่ได้ (ตรงกับเอกสารข้อ 1.2)
- เดือนในอีเมลไม่ตรงกับเดือนในไฟล์ → บันทึกไม่ได้ (หยิบไฟล์ผิดฉบับ)
- อีเมลที่เคยดึงเข้าระบบแล้วขึ้นป้าย "เอาเข้าระบบแล้ว" กันกดซ้ำ

### ขั้นที่ 4 — สร้างร่างใน Gmail

`POST /api/cycles/:c/:p/gmail-draft` วางร่างไว้ในกล่อง Drafts พร้อมลิงก์เปิดตรงไปที่ร่างนั้น

> **ระบบไม่ส่งอีเมลเอง และส่งไม่ได้ด้วย** — `src/integrations/gmail.js` ไม่มีการเรียก
> `messages/send` อยู่เลย Google ไม่มี scope ที่ให้ "สร้างร่างได้แต่ส่งไม่ได้"
> หลักประกันจึงอยู่ที่ตัวโค้ด ไม่ใช่ที่ scope — ตรงกับ `flowaccount.js` ที่ไม่มีโค้ดกดอนุมัติเอกสาร
>
> ยังไม่มีไฟล์แนบในร่าง เพราะ PDF ใบแจ้งหนี้อยู่ใน FlowAccount ต้องทำข้อ 4.3 ก่อน

### บั๊กที่เจอระหว่างทางและแก้แล้ว

| บั๊ก | อาการ | ต้นเหตุ |

| **ชื่อผู้กดเป็นคนที่ไม่ได้กด** | บันทึกว่า "กิตติมา สังข์ทอง" อนุมัติวางบิล | ค่าเริ่มต้นของ `ACTOR` ถูกตั้งเป็นชื่อผู้จัดทำใบว่าจ้างฝั่งลูกค้า → เปลี่ยนเป็น "ยังไม่ได้ระบุผู้ใช้" และให้แถบบนแสดงค่าเดียวกับที่บันทึกจริง |
| **`.env` ไม่เคยถูกอ่าน** | ใส่ `ANTHROPIC_API_KEY` แล้วระบบยังบอกว่าไม่มี | Node ไม่โหลด `.env` ให้เอง และ `package.json` ไม่ได้สั่ง `--env-file` → เพิ่ม `src/env.js` |
