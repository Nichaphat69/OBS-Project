# ภาพรวมระบบวางบิล Outsource อัตโนมัติ (OBS)

> เอกสารนี้เขียนจากโค้ดจริง ทุกข้อตรวจกับไฟล์ในโปรเจคแล้ว

## 1. ระบบนี้คืออะไร

**Outsource Billing System (OBS)** เป็นเครื่องมือภายในฝ่ายบัญชีของ iPassion Co., Ltd.
สำหรับวางบิลค่าจ้างพนักงาน Outsource ที่ไปประจำอยู่ที่ออฟฟิศลูกค้า

ระบบรับช่วงงานเอกสารตั้งแต่**อีเมลแจ้งอนุมัติ Timesheet เข้ามา** จนถึง**ร่างใบแจ้งหนี้และร่างอีเมลวางไว้ให้**
เหลือให้คนทำเพียง **ตรวจ · กดอนุมัติ · เซ็น · กดส่ง**

หลักการที่คุมทั้งระบบ:
> ระบบเตรียมเอกสารให้เสร็จ แต่ไม่ตัดสินใจแทนคน — ทุกใบยังต้องมีคนตรวจและกดเอง

**ลูกค้าที่ใช้ตั้งต้นระบบ** — บริษัท ไทยประกันชีวิต จำกัด (มหาชน)
สัญญา จซ.002/2569 · ใบว่าจ้าง 26/B0113 · โครงการ Outsource for BAU Project · พนักงาน 2 คน · 6 เดือน

ระบบออกแบบให้รองรับหลายลูกค้าและหลายสัญญา ไม่ได้ผูกกับไทยประกันชีวิตรายเดียว

## 3. ตรรกะการคิดเงิน

### สัญญานี้คิดแบบเหมาเดือน ไม่ใช่นับวัน

จุดที่เข้าใจผิดกันบ่อยที่สุด — **ไม่ใช่** `จำนวนวันที่มาทำงาน × อัตราต่อวัน`

```
ยอดของพนักงาน 1 คน = เรทรายเดือนเต็มจำนวน − (จำนวนวันลา × อัตราต่อวัน)
```

ในใบแจ้งหนี้ ช่องจำนวนจะเป็น **`1 Months` เสมอ** และวันลาไปโผล่ในช่อง**ส่วนลด** ไม่ได้ไปลดจำนวนวัน

```
อัตราต่อวัน = เรทรายเดือน ÷ จำนวนวันทำงานมาตรฐานของเดือนนั้น
```

### ลำดับการคิดภาษี

## 4. การตรวจสอบความถูกต้อง

`src/domain/manday.js` ตรวจ **5 เรื่อง แตกเป็น 8 เงื่อนไข** ผลออกมา 3 ระดับ

| ระดับ | ความหมาย |
|---|---|
| `pass` ผ่าน | ไปต่อได้ |
| `warn` เตือน | ไปต่อได้ แต่ให้คนอ่านก่อน |
| `fail` ไม่ผ่าน | **กดอนุมัติไม่ได้** จนกว่าจะแก้ |

| เรื่องที่ตรวจ | รหัส | ระดับ | เงื่อนไข |
|---|---|---|---|
| 1. ผลรวมวันตรงกับปฏิทิน | `workday_sum` | pass / **fail** | วันทำงานที่รายงาน + วันลา ต้องเท่ากับวันทำงานของเดือน |
| 2. วันลาอยู่ในรอบบิล | `leave_out_of_period` | **fail** | วันลาที่ระบุมาไม่ได้อยู่ในเดือนนั้น |
| 2. วันลาไม่ตรงเสาร์–อาทิตย์ | `leave_on_weekend` | **fail** | ลาในวันที่ไม่ใช่วันทำงาน = กรอกผิด ไม่ควรหักเงิน |
| 2. วันลาไม่ตรงวันหยุด | `leave_on_holiday` | **fail** | เหตุผลเดียวกัน |
| 3. ป้ายกำกับตรงกับปฏิทิน | `label_mismatch` | warn | Timesheet เขียน "Holiday" ในวันเสาร์–อาทิตย์ · ไม่กระทบยอดเงิน |
| 4. ตัวหารยืนยันได้ | `divisor_ambiguous` | warn | เดือนนั้นวันทำงานเท่ากับตัวหารคงที่พอดี แยกไม่ออกว่าใช้แบบไหน |
| 4. ตัวหารตรงกับความจริง | `divisor_differs` | warn | ใช้ตัวหารคงที่ แต่เดือนนั้นวันทำงานจริงไม่เท่า |
| 5. วันที่คิดเงินไม่ติดลบ | `payable_negative` | **fail** | วันลามากกว่าวันทำงานมาตรฐาน = ข้อมูลผิด |

**ข้อสำคัญ** — มีแค่ `workday_sum` ที่ขึ้นรายการทั้งตอนผ่านและไม่ผ่าน
ข้ออื่นจะ**โผล่มาเฉพาะเมื่อมีปัญหา** ถ้าไม่มีปัญหาก็ไม่มีรายการนั้นเลย
เพราะฉะนั้นเวลาเห็น "ผ่าน 1 · ทักไว้ 1 · ไม่ผ่าน 0" คือปกติ ไม่ได้แปลว่าตรวจไม่ครบ

### วิธีแก้ — จับคู่ 3 ชั้น (`src/domain/matching.js`)

| ชั้น | วิธี | ผลลัพธ์ |
|---|---|---|
| 1 · `EXACT` | ชื่อตรงกับฐานข้อมูล (หลัง normalize) | ใช้ได้เลย |
| 2 · `ALIAS` | ตรงกับตารางชื่อพ้อง `employee_aliases` | ใช้ได้เลย |
| 3 · `FUZZY` | ระยะห่าง Levenshtein ≤ 2 ตัวอักษร | เดาให้ แต่**ขอให้คนยืนยัน** |
| — · `NONE` | จับคู่ไม่ได้ | **ไม่บันทึกและไม่เดา** — แจ้งให้ไปเพิ่มชื่อพ้องก่อน |

### กฎที่กันความผิดพลาด

- **ตำแหน่งที่ขึ้นบนใบแจ้งหนี้ ใช้ค่าจาก `employees.invoice_position` เสมอ** ไม่เอาจาก Timesheet
- ทุกชื่อพ้องบันทึกด้วยว่าเจอในเอกสารใบไหน (`employee_aliases.source`)
- ถ้าตำแหน่งใน Timesheet ไม่ตรงกับฐานข้อมูล ระบบทักไว้ แต่ยอดเงินยังใช้เรทจากฐานข้อมูล

## 9. การทำงานอัตโนมัติด้วย n8n

**n8n รับหน้าที่จุดชนวนและตั้งเวลา · OBS รับหน้าที่คิดเงิน**

กฎการคิดเงินทั้งหมดอยู่ใน OBS และมีชุดทดสอบคุม n8n ไม่ต้องรู้กฎเลย แค่ส่งไฟล์เข้ามาแล้วอ่าน `nextAction`
ถ้าวันหลังเปลี่ยนจาก n8n ไปใช้อย่างอื่น ตัวคิดเงินไม่ต้องแก้

## 12. สิ่งที่ระบบไม่ทำ — ตั้งใจให้เป็นแบบนี้

ไม่ใช่ข้อจำกัด แต่เป็นเส้นที่ตกลงกันไว้ว่าคนต้องเป็นคนตัดสินใจ

| ระบบไม่ทำ | เหตุผล |
|---|---|
| ไม่ออกเอกสารตัวจริง | สร้างเป็นร่างใน FlowAccount เท่านั้น |
| **ไม่ส่งอีเมลเอง** | ร่างหัวเรื่องและเนื้อความไว้ให้ คนอ่านทวนแล้วกดส่ง |
| ไม่เซ็นเอกสาร | ลายเซ็นและตราประทับเป็นงานคน รวมถึงการนำเอกสารไปวางบิลที่อาคารลูกค้า |
| ไม่ข้ามข้อที่ตรวจไม่ผ่าน | มี `fail` ค้างอยู่ = ปุ่มอนุมัติถูก disable และ API คืน `409` |
| ไม่เดาเมื่อจับคู่ชื่อไม่ได้ | ไม่บันทึกเลย แจ้งให้คนไปเพิ่มชื่อพ้องก่อน |
| ไม่บันทึกการรับเงิน | สถานะชำระจริงอยู่ที่ FlowAccount ระบบนี้ไม่ติดตามลูกหนี้ (เอาออกแล้วเพราะเกินขอบเขต — ดู `scope-audit.md`) |

## 5. ✅ แก้แล้ว 31 ก.ค. 69 — ประตูมนุษย์อยู่ผิดขั้น

n8n workflow ทั้งสองไฟล์เดิม**ยิงสร้างร่างเองโดยไม่มีคนมาเกี่ยวเลย**

```
01-ingest:  Gmail → IF อนุมัติ → ingest → switch → สร้างร่างใน FlowAccount     ← ไม่มีคน (ของเดิม)
02-daily:   ทุกวัน 09:00 → /cycles/ready → IF → สร้างร่างใน FlowAccount        ← ไม่มีคน (ของเดิม)
```

### ที่แก้ไปแล้ว
ทั้งสอง workflow เปลี่ยนไปเรียก **`POST /api/cycles/:id/:period/request-approval`** แทน `/approve`
ตรงๆ — endpoint นี้แค่ส่ง Flex Message สรุปรอบบิล (ลูกค้า โครงการ จำนวนคน ยอดรับชำระ) พร้อมปุ่ม
"อนุมัติ"/"ตีกลับ" เข้า LINE (`src/integrations/line.js`) **ยังไม่สร้างเอกสารใดๆ**

ร่างใน FlowAccount จะเกิดต่อเมื่อมีคนกดปุ่มใน LINE จริงๆ — OBS รับ webhook เองที่
`POST /api/line/webhook` (ตรวจลายเซ็น HMAC + ตรวจ `userId` อยู่ในรายชื่อ `LINE_APPROVER_USER_IDS`
ก่อนเชื่อ) แล้วเรียก `approveCycle()` ตัวเดิมให้ ดู `src/service.js` → `requestCycleApproval()` /
`decideCycleApproval()` / `processLineWebhook()` และเทสต์ใน `test/line-approval.test.js` (12 ข้อ)

### ทำไมรับ webhook ที่ OBS เอง ไม่ผ่าน n8n ตามที่วางแผนไว้เดิม
แผนเดิม (หัวข้อ 10 เวอร์ชันก่อนหน้า) จะให้ LINE ยิง webhook เข้า n8n ก่อน แล้ว n8n ค่อยเรียก OBS
แต่ OBS มีเซิร์ฟเวอร์ HTTP ของตัวเองอยู่แล้ว การรับตรงจึงตัดการเรียกซ้อนหนึ่งชั้น และไม่ต้องเขียน
ตรรกะตรวจลายเซ็น/ตรวจสิทธิ์ซ้ำสองที่ (n8n + OBS) — ยังไม่ได้ยิง end-to-end จริงเพราะยังไม่มี
LINE Developers channel ให้ทดสอบ (ต้องขอ credential จากคน ดูหัวข้อ 8)

### ปุ่มบนหน้าเว็บ "อนุมัติและสร้างร่างใน FlowAccount" ยังเรียก `/approve` ตรงเหมือนเดิม

## 11. ✅ เพิ่มนอกเอกสาร 31 ก.ค. 69 — ระบบ login + role

- ตาราง `users` / `sessions` ใน schema
- 2 role: `admin` (แก้ข้อมูลหลักได้) / `operator` (งานประจำวันได้แต่แก้ข้อมูลหลักไม่ได้)
- ทุก endpoint ต้อง login ยกเว้น `/auth/*`, `/timesheets/ingest`, `/cycles/ready`,
  `/cycles/.../request-approval`, `/line/webhook` (จุดที่ n8n/LINE เรียกตรง ไม่มี cookie)

- เทสต์ 13 ข้อ (`test/auth.test.js`) + ทดสอบจริงผ่านเบราว์เซอร์ครบ (login/logout/403 ของ operator)

## 12. ✅ เปลี่ยนแล้ว 3 ส.ค. 69 — เลิกใช้ Claude API ทั้งระบบ ย้ายไปโมเดลในเครื่อง

เอกสารออกแบบเดิม (ข้อ 1.4, 4.4) ระบุ Claude API ชัดเจน แต่ตัดสินใจไม่ใช้บริการ AI ภายนอกเลย —
ย้ายทั้งสองจุดไปเรียกโมเดลที่รันในเครื่องแทน (LM Studio/Ollama ผ่าน endpoint แบบ OpenAI-compatible)

**ทำอะไรไปแล้ว**
- ถอด `@anthropic-ai/sdk` ออกจาก dependency ทั้งหมด เพิ่ม `pdf-to-img` แทน (แปลง PDF → รูปภาพ
  ก่อนส่งให้โมเดล vision — ทดสอบแล้วว่าใช้งานได้จริงโดยไม่ต้องพึ่ง native lib เพิ่ม เช่น ImageMagick/Poppler)
- `src/llm/localClient.js` (ใหม่) — ตัวกลางเรียกโมเดลในเครื่อง ใช้ร่วมกันทั้งสองจุด บังคับคำตอบเป็น
  JSON ด้วย `response_format: {type: 'json_schema', json_schema: {strict: true, schema}}`
  (LM Studio ไม่รับ `json_object` — ทดสอบยิงตรงแล้วโดน 400 จึงแก้เป็น `json_schema` แบบ strict)
  แล้วตรวจคีย์ที่ต้องมีซ้ำด้วยโค้ดอีกชั้นเผื่อโมเดลตอบไม่ครบ
- `src/extract/timesheet.js` — อ่าน PDF ด้วยโมเดล **vision** (`LOCAL_LLM_VISION_MODEL`) แทน Claude
- `src/llm/email.js` — ร่าง/อ่านอีเมลด้วยโมเดล **ข้อความล้วน** (`LOCAL_LLM_MODEL`) แทน Claude
- เอา gate ตรวจ `ANTHROPIC_API_KEY` ออกจาก `server.js` ทุกจุด (local ไม่ต้องมี API key)
- อัปเดตหน้าตั้งค่าให้แสดงสถานะโมเดลในเครื่องแทน "Claude API"
- **3–4 ส.ค. 69 (เพิ่มหลังพบปัญหาจริง)** — เปลี่ยนจากส่งทั้งไฟล์ PDF หลายหน้า+schema ใหญ่ในคำขอเดียว
  (โมเดลปฏิเสธตอบ "I cannot fulfill this request" เมื่อรูปเกิน 3-4 หน้า) เป็น **อ่านทีละหน้า + รวมผล
  ด้วยโค้ด** (`mergePageResults()`) — หน้าที่อ่านไม่สำเร็จแค่บางหน้าไม่ทำให้ทั้งฉบับพัง เดาแบบ "ไม่เห็นค่านี้
  ในหน้านี้" ได้อย่างสุจริตเพราะ Timesheet จริงเป็น Excel export แยกหน้าซ้าย (ตาราง)/หน้าขวา (ชื่อ+เซ็น)
- เปลี่ยนโมเดลจาก `google/gemma-3-4b` เป็น **`google/gemma-4-e2b`** (ทั้ง `LOCAL_LLM_MODEL` และ
  `LOCAL_LLM_VISION_MODEL` — เครื่องนี้โหลดสองโมเดลพร้อมกันไม่ไหว จึงใช้ตัวเดียวกันทั้งสองงาน) แม่นกว่า
  แต่ช้ากว่าเดิมมาก (~4 นาที/ไฟล์)

**ทำไมถึงยอมรับ trade-off นี้**
- โมเดล vision ในเครื่องแม่นน้อยกว่า Claude ชัดเจนโดยเฉพาะกับ PDF สแกน/เอียง — ยอมรับความเสี่ยงนี้แล้ว
  เพราะ `verifyExtraction()` ยังตรวจซ้ำด้วยโค้ดเหมือนเดิมทุกจุด และคนยังต้องยืนยันก่อนบันทึกเสมอ
  (โหมด manual) — Gemma รุ่น 2B ธรรมดาเป็น text-only ทำ vision ไม่ได้เลย ต้องใช้รุ่นที่รองรับภาพ

**ยังต้องทำเอง**
- เปิด Local Server ใน LM Studio (หรือรัน Ollama) ให้พร้อมก่อนใช้งานทั้งสองฟีเจอร์เสมอ — ไม่มี
  fallback ไปที่บริการภายนอกแล้ว ถ้า local server ไม่รันจะ error ทันที (ข้อความบอกชัดว่าต้องเปิดอะไร)
- ตั้งชื่อโมเดลใน `.env` (`LOCAL_LLM_MODEL`, `LOCAL_LLM_VISION_MODEL`) ให้ตรงกับที่โหลดไว้จริงในเครื่อง

## เกินขอบเขต — 3 รายการ

### 1. โมดูลรายงานภาษี · 229 บรรทัด · **ควรตัดสินใจ**

| ไฟล์ | บรรทัด |
|---|---|

| `service.js` → `reportCsv()` | 46 |
| `app.js` → `renderReports()` | 102 |
| `server.js` → `GET /api/reports` และ `GET /api/reports/export/:type` | 2 route |

มีอะไรอยู่ในนั้น — รายงานภาษีขาย VAT · รายงานภาษีหัก ณ ที่จ่าย · สรุปรายพนักงาน ·
สรุปวันลาแยกประเภท · ส่งออก CSV 3 ไฟล์

**ทำไมถือว่าเกิน** — ทั้งหมดนี้เป็นงาน**ยื่นภาษีและปิดบัญชี** ไม่ใช่งานวางบิล
ไม่มีอยู่ในขอบเขต 4 ข้อ และไม่มีอยู่ในเอกสาร workflow แม้แต่บรรทัดเดียว

**ข้อควรพิจารณา** — ถ้าฝ่ายบัญชีเอาไปใช้ยื่นภาษีจริงทุกเดือน ก็มีประโยชน์และเก็บไว้ได้
แต่ถ้าไม่ได้ใช้ ควรลบออก เพราะเป็นโค้ดที่ต้องดูแลต่อโดยไม่มีใครใช้

### 2. การติดตามการรับชำระ (AR) · **ควรเอาออก**

| จุด | อยู่ที่ไหน |
|---|---|
| การ์ด "รอรับชำระ" บนแดชบอร์ด | `app.js` → `renderDashboard` |
| `receivable` (outstanding · overdueAmount · overdueCount · nextDueDate) | `service.js` → `dashboard()` |
| แจ้งเตือน "ใบแจ้งหนี้เกินกำหนดชำระ" ระดับ critical | `service.js` → `notifications()` |

**ทำไมถือว่าเกิน และทำไมควรเอาออกจริงๆ**

ไม่ใช่แค่เกินขอบเขต แต่**ให้ข้อมูลที่อาจทำให้เข้าใจผิดได้** —
ระบบไม่ได้บันทึกการรับเงินเลย สถานะชำระจริงอยู่ที่ FlowAccount
ยอด "รอรับชำระ" จึงคำนวณจาก**วันครบกำหนดตามเครดิตล้วนๆ**

แปลว่าถ้าลูกค้าจ่ายเงินแล้ว ระบบก็ยังขึ้นว่า "เกินกำหนดชำระ" อยู่ดี
และขึ้นเป็นการแจ้งเตือนระดับ **critical** สีแดงบนกระดิ่ง ซึ่งจะทำให้คนไล่ตามเรื่องที่จบไปแล้ว

ตอนนี้กันไว้ด้วยกล่องข้อความเตือนท้ายแดชบอร์ดเท่านั้น ซึ่งพึ่งได้ไม่มากพอ

### 3. กราฟและความคืบหน้าสัญญาบนแดชบอร์ด · **เก็บไว้ได้**

กราฟมูลค่าวางบิลรายเดือน · แถบความคืบหน้าสัญญา · `monthlySeries()` · `trends`

ไม่ได้อยู่ใน 4 ข้อ แต่เป็นการสรุปข้อมูลที่ระบบมีอยู่แล้ว ไม่ได้สร้างข้อมูลใหม่
ไม่ทำให้เข้าใจผิด และช่วยให้เห็นภาพรวมเมื่อเปิดระบบ — เก็บไว้ไม่เสียหาย

## จุดที่ใช้ LLM (โมเดลในเครื่อง — LM Studio/Ollama) — มี 2 จุด ไม่ควรมีมากกว่านี้

| จุด | ทำอะไร | ทำไมต้องเป็น LLM | กันพลาดยังไง |
|---|---|---|---|
| **1.1 อ่าน Timesheet PDF** | อ่านตาราง 28–31 แถว · ชื่อ · ตำแหน่ง · วันลา · ลายเซ็น | ไฟล์เป็น PDF export จาก Excel มีภาษาไทยผสม · text extraction ธรรมดาได้ตัวอักษรเพี้ยน | บังคับ JSON schema · `verifyExtraction()` ตรวจซ้ำด้วยโค้ด · คนดูก่อนบันทึก (โหมด Manual) |
| **4 ร่างอีเมล** | เรียบเรียงตัวเลขเป็นภาษาคน + อธิบายว่าเดือนนี้ต่างจากเดือนก่อนเพราะอะไร | template เขียนได้แค่สิ่งที่เดาไว้ล่วงหน้า เหตุผลที่ยอดต่างเปลี่ยนทุกเดือน | **ห้ามคิดเลขเอง** — ส่งเฉพาะตัวเลขที่คำนวณแล้วให้เรียบเรียง · ยังไม่ส่งออกจนคนกด |

**จุดที่จงใจไม่ใช้ LLM** — คิดเงิน · นับวันทำงาน · ตัดสินว่าผ่าน/ไม่ผ่าน · ประกอบ payload
ทั้งหมดเป็นโค้ดที่มีชุดทดสอบ 27 ข้อคุมไว้ ตรวจตรงกับใบแจ้งหนี้จริง INV2026020006 ทุกบรรทัด
เรื่องเงินให้โมเดลตัดสินไม่ได้ เพราะทวนย้อนกลับไม่ได้ว่าทำไมถึงได้ตัวเลขนั้น

## หน้าจอในโหมด Manual — เหลือ 5 หน้า

เดิม 8 แท็บ ตัดเหลือ 5 ตามหลัก: **หน้านั้นเป็นขั้นตอนที่คนต้องลงมือทำหรือไม่**
บวกแดชบอร์ดอีกหน้าที่เก็บไว้เพราะใช้ดูภาพรวมได้ แม้ไม่ใช่ขั้นตอนงาน

| เมนู | คือขั้นไหน | คนทำอะไรที่นี่ |
|---|---|---|
| **แดชบอร์ด** | — (หน้าแรก) | ดูภาพรวม: เงินค้างอยู่ขั้นไหน · กราฟมูลค่ารายเดือน · สัดส่วนสถานะรอบบิล · **งานที่ต้องทำ** เรียงตามสิ่งที่กดต่อได้เลย · ความคืบหน้าสัญญา · ล่าสุดในระบบ |
| **1 · อัปโหลด Timesheet** | ขั้น 1 | ลากไฟล์มาวาง → ให้ AI อ่าน → ตรวจสิ่งที่อ่านได้ → กดยืนยันบันทึก · (มีแท็บ "กรอกเอง" ไว้ใช้ตอนไฟล์อ่านไม่ออก) |
| **2 · ตรวจ Manday** + หน้าตรวจ | ขั้น 2 | อ่านปฏิทินและผลตรวจ → **กดยืนยันว่าตรวจแล้ว** หรือ ตีกลับ |
| **3 · วางบิล & ร่างอีเมล** + หน้าอนุมัติ | ขั้น 3–4 | ดูใบแจ้งหนี้จำลอง → กดอนุมัติสร้างร่าง → ให้ AI ร่างอีเมล → คัดลอกไปส่ง → บันทึกว่าส่งแล้ว |
| **ข้อมูลหลัก** | ไม่ใช่ขั้นตอน | เข้ามาแก้เมื่อขั้น 2 บอกว่าจับคู่ชื่อไม่ได้ · เรทไม่ตรง · วันหยุดขาด |

## สวิตช์สลับโหมด

```
billing_rules.requireHumanCheck = true    ← ตอนนี้ (Manual)
```
* รอบบิลที่ครบทุกคนและตรวจผ่าน จะได้สถานะ **"รอคนตรวจ"** ไม่ใช่ "รออนุมัติ"
* `/cycles/ready` ไม่คืนรอบนั้น → n8n ตัวตั้งเวลาจะยังไม่แตะ
* `/approve` ตอบ 409 พร้อมบอกชื่อคนที่ยังไม่มีใครยืนยัน

```
billing_rules.requireHumanCheck = false   ← โหมด Auto
```
* ขั้น 1.2 กับ 2.1 หายไป ระบบไหลจาก `/ingest` → `/approve` เองได้
* คนยังต้องกดอนุมัติที่หน้ารอบบิลอยู่ดีถ้าไม่เปิด n8n ตัวตั้งเวลา

### ตราประทับ "คนตรวจแล้ว" หมดอายุเองได้

ตราไม่ได้ผูกกับใบ แต่ผูกกับ **ยอดชุดที่คนเห็นตอนกด** (`lineAmount` + `payableDays`)
ถ้ายอดเปลี่ยนหลังจากนั้น — ลูกค้าส่ง Timesheet ฉบับแก้มาทับ · มีคนเพิ่มวันหยุด · แก้เรท —
ตราจะกลายเป็น "ยอดเปลี่ยนหลังยืนยันไปแล้ว" และรอบบิลกลับไปติดที่ขั้น 2 อีกครั้ง
ไม่งั้นจะมีคนอนุมัติยอดที่ไม่เคยมีใครดู (มีชุดทดสอบคุมกรณีนี้ไว้)

## เพิ่มเติม 31 ก.ค. 2569 (รอบสาม) — ต่อ Gmail + เอา 2 หน้ากลับ

### ขั้นที่ 1 มี 3 ทางแล้ว

| ทาง | คนทำอะไร | ระบบทำอะไร | ใช้เมื่อ |
|---|---|---|---|
| **ดึงจาก Gmail** | กด "ดึงรายการเมล" → เลือกฉบับ → กด "ให้ AI อ่าน" | ดึงไฟล์แนบ + **อ่านเนื้อเมลด้วย LLM** → ได้เลขที่เอกสาร · สถานะ "อนุมัติ" · ผู้อนุมัติ · วันที่ | ต่อ Gmail แล้ว — ใกล้โหมด Auto ที่สุด |
| **อัปโหลดไฟล์** | ลากไฟล์ PDF มาวาง + พิมพ์เลขที่เอกสารเอง | AI อ่านเฉพาะไฟล์ | ไม่อยากต่อ Gmail |
| **กรอกเอง** | กรอก 6 ช่อง + วันลา | สร้างตารางรายวันจากปฏิทิน | ไม่มี API key หรือไฟล์อ่านไม่ออก |

ทั้งสามทางไปจบที่หน้าจอเดียวกัน — **ให้คนตรวจสิ่งที่อ่านได้แล้วกดยืนยัน** จึงบันทึก

**ตัวกันพลาดที่ได้มาจากการอ่านเนื้อเมล** (ทำในโค้ด ไม่ใช่ให้โมเดลตัดสิน)
- อีเมลไม่ได้เขียนว่า "อนุมัติ" → บันทึกไม่ได้ (ตรงกับเอกสารข้อ 1.2)
- เดือนในอีเมลไม่ตรงกับเดือนในไฟล์ → บันทึกไม่ได้ (หยิบไฟล์ผิดฉบับ)
- อีเมลที่เคยดึงเข้าระบบแล้วขึ้นป้าย "เอาเข้าระบบแล้ว" กันกดซ้ำ

### ขั้นที่ 4 — สร้างร่างใน Gmail

`POST /api/cycles/:c/:p/gmail-draft` วางร่างไว้ในกล่อง Drafts พร้อมลิงก์เปิดตรงไปที่ร่างนั้น

> **ระบบไม่ส่งอีเมลเอง และส่งไม่ได้ด้วย** — `src/integrations/gmail.js` ไม่มีการเรียก
> `messages/send` อยู่เลย Google ไม่มี scope ที่ให้ "สร้างร่างได้แต่ส่งไม่ได้"
> หลักประกันจึงอยู่ที่ตัวโค้ด ไม่ใช่ที่ scope — ตรงกับ `flowaccount.js` ที่ไม่มีโค้ดกดอนุมัติเอกสาร
>
> ยังไม่มีไฟล์แนบในร่าง เพราะ PDF ใบแจ้งหนี้อยู่ใน FlowAccount ต้องทำข้อ 4.3 ก่อน

### บั๊กที่เจอระหว่างทางและแก้แล้ว

| บั๊ก | อาการ | ต้นเหตุ |
|---|---|---|
| **เวลาเพี้ยน 7 ชั่วโมง** | เพิ่งกดไป กระดิ่งขึ้น "7 ชั่วโมงที่แล้ว" | SQLite `datetime('now')` คืน UTC โดยไม่มีเครื่องหมายเขตเวลา หน้าจอตีเป็นเวลาไทย → เปลี่ยนเป็น `strftime(...'Z')` และให้ฝั่งหน้าจอตีสตริงเปล่าเป็น UTC |
| **ชื่อผู้กดเป็นคนที่ไม่ได้กด** | บันทึกว่า "กิตติมา สังข์ทอง" อนุมัติวางบิล | ค่าเริ่มต้นของ `ACTOR` ถูกตั้งเป็นชื่อผู้จัดทำใบว่าจ้างฝั่งลูกค้า → เปลี่ยนเป็น "ยังไม่ได้ระบุผู้ใช้" และให้แถบบนแสดงค่าเดียวกับที่บันทึกจริง |
| **`.env` ไม่เคยถูกอ่าน** | ใส่ `ANTHROPIC_API_KEY` แล้วระบบยังบอกว่าไม่มี | Node ไม่โหลด `.env` ให้เอง และ `package.json` ไม่ได้สั่ง `--env-file` → เพิ่ม `src/env.js` |
| **แถบสัดส่วนสถานะไม่ขึ้น** | ช่องว่างเปล่าใต้หัวข้อ | `.split` มี HTML แต่ไม่เคยมี CSS |

## หน้า 3 · รอบบิล

```
ออกแบบหน้ารอบบิล ใช้ติดตามว่าแต่ละเดือนของแต่ละสัญญาเดินไปถึงขั้นไหนแล้ว
หน้านี้ต้องแสดงทุกเดือนตามช่วงสัญญา รวมเดือนที่ยังไม่ได้รับ Timesheet ด้วย
เพราะเดือนที่ยังไม่ได้เอกสารคือเดือนที่ต้องไปตามทวงลูกค้า

ส่วนหัวเรื่อง
บรรทัดเล็กสีน้ำเงิน "รอบบิลรายเดือน · ข้อมูล ณ 28 กรกฎาคม 2569"
หัวเรื่องใหญ่ "รอบบิล"
บรรทัดสีเทา "ทุกเดือนตามช่วงสัญญา รวมเดือนที่ยังไม่ได้รับ Timesheet · เลือกรอบเพื่อดูใบแจ้งหนี้และอนุมัติ"

ถัดลงมา การ์ดสรุปสัญญาเต็มความกว้างหนึ่งใบต่อหนึ่งสัญญา
  หัวการ์ด "26/B0113 — บริษัท ไทยประกันชีวิต จำกัด (มหาชน)"

  ข้างในบนสุดเป็นสี่ช่องเรียงแนวนอน แต่ละช่องมีชื่อเล็กสีเทาอยู่บนและตัวเลขใหญ่อยู่ล่าง
  พร้อมหน่วย "บาท" หรือ "เดือน" ตัวเล็กต่อท้าย
    "มูลค่าสัญญา 1,058,183.58 บาท" | "วางบิลแล้ว 0.00 บาท" (ตัวเลขสีน้ำเงิน) |
    "คงเหลือ 1,058,183.58 บาท" (ตัวเลขสีแดงเข้ม) | "รอบบิล 0 / 6 เดือน"
  ถัดลงมาเป็นแถบความคืบหน้าแนวนอนบาง เติมสีน้ำเงินจากซ้าย
  ใต้แถบสามข้อความชิดซ้าย กลาง ขวา "1 ม.ค. 2569" | "0% ของสัญญา" | "30 มิ.ย. 2569"

ถัดลงมา การ์ดตารางรอบบิลเต็มความกว้าง
  บนสุดของการ์ดเป็นแถบเครื่องมือ ซ้ายเป็นกลุ่มปุ่มกรองสี่ปุ่มติดกัน
  ปุ่มที่เลือกพื้นน้ำเงินตัวอักษรขาว แต่ละปุ่มมีชื่อและตัวเลขนับในวงกลมเล็ก
  "ทุกรอบ 6" (เลือกอยู่) "ต้องดำเนินการ 6" "รอ Timesheet 5" "วางบิลแล้ว 0"
  ขวาสุดข้อความสีเทา "แสดง 6 จาก 6 รอบ"

  ตารางห้าคอลัมน์ หัวตารางพื้นเทาอ่อนตัวหนา
  รอบบิล | Timesheet | สถานะ | กำหนดเวลา | มูลค่า (ชิดขวา)
  คอลัมน์รอบบิลแสดงชื่อเดือนตัวหนา และบรรทัดเล็กสีเทาใต้ชื่อบอกจำนวนคนในสัญญา
  คอลัมน์ Timesheet แสดงเป็นเศษส่วนตัวหนา เช่น "2 / 2" และมีแถบเล็กใต้ตัวเลขแสดงสัดส่วนที่ได้มาแล้ว
  คอลัมน์สถานะเป็นป้ายสี ห้าแบบตามนี้
    "รอ Timesheet" พื้นเทาอ่อน | "ได้ไม่ครบ" พื้นเหลืองอ่อน | "ข้อมูลไม่ตรง" พื้นแดงอ่อน |
    "รออนุมัติ" พื้นเหลืองอ่อนตัวอักษรน้ำตาลส้ม | "วางบิลแล้ว" พื้นเขียวอ่อน
  คอลัมน์กำหนดเวลาแสดงวันที่ควรวางบิล และถ้าเลยกำหนดแล้วให้มีคำว่า "เลยกำหนด" สีแดงต่อท้าย
  หกแถว
    "มกราคม 2569" · "2 / 2" · ป้าย "รออนุมัติ" · "ควรวางบิล 2 ก.พ. 2569 · เลยกำหนด" · "173,716.73"

  ทุกแถวต้องดูเหมือนกดได้ มีเอฟเฟกต์เมื่อเอาเมาส์ชี้
```
