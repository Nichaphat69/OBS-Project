## เกินขอบเขต — 3 รายการ

### 1. โมดูลรายงานภาษี · 229 บรรทัด · **ควรตัดสินใจ**

| ไฟล์ | บรรทัด |
|---|---|
| `service.js` → `reports()` | 81 |
| `service.js` → `reportCsv()` | 46 |
| `app.js` → `renderReports()` | 102 |
| `server.js` → `GET /api/reports` และ `GET /api/reports/export/:type` | 2 route |

มีอะไรอยู่ในนั้น — รายงานภาษีขาย VAT · รายงานภาษีหัก ณ ที่จ่าย · สรุปรายพนักงาน ·
สรุปวันลาแยกประเภท · ส่งออก CSV 3 ไฟล์

**ทำไมถือว่าเกิน** — ทั้งหมดนี้เป็นงาน**ยื่นภาษีและปิดบัญชี** ไม่ใช่งานวางบิล
ไม่มีอยู่ในขอบเขต 4 ข้อ และไม่มีอยู่ในเอกสาร workflow แม้แต่บรรทัดเดียว

**ข้อควรพิจารณา** — ถ้าฝ่ายบัญชีเอาไปใช้ยื่นภาษีจริงทุกเดือน ก็มีประโยชน์และเก็บไว้ได้
แต่ถ้าไม่ได้ใช้ ควรลบออก เพราะเป็นโค้ดที่ต้องดูแลต่อโดยไม่มีใครใช้

### 2. การติดตามการรับชำระ (AR) · **ควรเอาออก**

| จุด | อยู่ที่ไหน |
|---|---|
| การ์ด "รอรับชำระ" บนแดชบอร์ด | `app.js` → `renderDashboard` |
| `receivable` (outstanding · overdueAmount · overdueCount · nextDueDate) | `service.js` → `dashboard()` |
| แจ้งเตือน "ใบแจ้งหนี้เกินกำหนดชำระ" ระดับ critical | `service.js` → `notifications()` |

**ทำไมถือว่าเกิน และทำไมควรเอาออกจริงๆ**

ไม่ใช่แค่เกินขอบเขต แต่**ให้ข้อมูลที่อาจทำให้เข้าใจผิดได้** —
ระบบไม่ได้บันทึกการรับเงินเลย สถานะชำระจริงอยู่ที่ FlowAccount
ยอด "รอรับชำระ" จึงคำนวณจาก**วันครบกำหนดตามเครดิตล้วนๆ**

แปลว่าถ้าลูกค้าจ่ายเงินแล้ว ระบบก็ยังขึ้นว่า "เกินกำหนดชำระ" อยู่ดี
และขึ้นเป็นการแจ้งเตือนระดับ **critical** สีแดงบนกระดิ่ง ซึ่งจะทำให้คนไล่ตามเรื่องที่จบไปแล้ว

ตอนนี้กันไว้ด้วยกล่องข้อความเตือนท้ายแดชบอร์ดเท่านั้น ซึ่งพึ่งได้ไม่มากพอ

### 3. กราฟและความคืบหน้าสัญญาบนแดชบอร์ด · **เก็บไว้ได้**

กราฟมูลค่าวางบิลรายเดือน · แถบความคืบหน้าสัญญา · `monthlySeries()` · `trends`

ไม่ได้อยู่ใน 4 ข้อ แต่เป็นการสรุปข้อมูลที่ระบบมีอยู่แล้ว ไม่ได้สร้างข้อมูลใหม่
ไม่ทำให้เข้าใจผิด และช่วยให้เห็นภาพรวมเมื่อเปิดระบบ — เก็บไว้ไม่เสียหาย

## แก้การตัดสินใจ — 29 กรกฎาคม 2569 (รอบสอง)

**หน้าบันทึกการทำงาน — ลบออกแล้ว**

เดิมเอกสารนี้จัดว่าอยู่ในขอบเขต โดยอ้าง "Phase 2.6" ของเอกสาร workflow
ตรวจซ้ำแล้วยืนยันข้ออ้างนั้นไม่ได้ — เอกสาร workflow ต้นฉบับไม่ได้อยู่ในโปรเจกต์
และบรีฟที่บันทึกไว้เขียน Phase 2 ไว้แค่ว่า **"error path แจ้ง Slack/Line"** ไม่มีคำว่าหน้า log

เหตุผลจริงที่ผมยกให้หน้านี้คือ "บรีฟสั่งแจ้ง Slack/Line แต่ยังไม่ได้ต่อ
กระดิ่งกับหน้านี้จึงทำหน้าที่แทน" — ซึ่งเป็นการ**เอาสิ่งที่ยังไม่ได้ทำมาสร้างฟีเจอร์ใหม่กลบ**
แทนที่จะไปทำตามบรีฟ ผู้ใช้ตีตกเหตุผลนี้ และถูกต้อง

**เกณฑ์ที่ใช้ต่อจากนี้** — ฟีเจอร์ต้องสาวไปถึงบรรทัดในบรีฟได้
"ของที่บรีฟสั่งแต่ยังไม่ได้ทำ" ไม่ใช่ใบอนุญาตให้คิดของใหม่มาแทน

สิ่งที่ยังอยู่: ตาราง `audit_log` และ `logAudit()` เพราะเป็นกลไกใต้กระดิ่ง
(ที่ผู้ใช้สั่งให้ทำ) และเป็นตัวจุดชนวนการผลักข่าวสด ถอนออกคือกระดิ่งกับป้ายตัวเลขดับ

บันทึกไว้ตรงนี้เพื่อไม่ให้เข้าใจผิดว่าเอกสารสั่งให้ทำหน้าเว็บ

## ตัดของที่ไม่อยู่ในเอกสารออก — 30 กรกฎาคม 2569

ผู้ใช้สั่งให้ยึดเอกสารที่ส่งมาเป็นหลัก อะไรที่ไม่อยู่ในนั้นตัดทิ้งก่อน
เหตุผลที่สำคัญกว่าเรื่องขอบเขต — **ระบบนี้มีไว้แก้ปัญหาที่ของเดิมเป็น manual
หน้าจอที่บังคับให้คนไล่กดจึงขัดกับเป้าหมายของตัวเอง**

### แก้การตัดสินใจ — 31 ก.ค. 2569 (รอบสอง)

**เอาแดชบอร์ดกลับมา** — ผู้ใช้บอก *"อย่างน้อยแดชบอร์ดก็ใช้ดูข้อมูลได้"* ซึ่งถูกต้อง
เกณฑ์ "เป็นขั้นตอนที่คนต้องลงมือทำหรือไม่" ใช้ตัดสินหน้าที่**บังคับให้คนไล่กด**ได้ดี
แต่ใช้กับหน้าที่ไว้**ดู**อย่างเดียวไม่ได้ — หน้าดูไม่ได้เพิ่มงาน manual ให้ใคร

ของที่เอากลับมาไม่เหมือนเดิมทั้งหมด ปรับให้ตรงกับโหมด manual:
- KPI เปลี่ยนเป็น **ขั้น 2 รอคนตรวจ · ขั้น 3 ยืนยันแล้วรอวางบิล · วางบิลแล้ว** (เดิมคือ รออนุมัติ/ต้องตามทวง/วางบิลแล้ว)
- การ์ด "งานที่ต้องทำ" สร้างในตัว `dashboard()` เอง ไม่ต้องมี `notifications()` แยกอีก 60 บรรทัด
  และ**เรียงตามสิ่งที่กดทำต่อได้เลย** ไม่ใช่เรียงตามเลขขั้น — ไม่งั้นรายการตามทวง 5 รอบดันงานจริงตกจอ
- ไม่มีตัวเลข "รอรับชำระ" เหมือนที่เคยตัดไปเมื่อ 29 ก.ค. เพราะระบบไม่ได้บันทึกการรับเงิน
- เพิ่มสถานะ `checking` ลงในสัดส่วนสถานะรอบบิล และแปลชื่อ action ในบันทึกเป็นภาษาไทย
- แก้บั๊กเก่า: `.split` (แถบสัดส่วนสถานะ) มี HTML แต่ไม่เคยมี CSS จึงไม่เคยขึ้นอะไรเลย

**ใบแจ้งหนี้กับกระดิ่งยังไม่เอากลับ** — ข้อมูลของทั้งสองอยู่บนแดชบอร์ดแล้ว
(เลขที่ใบ + สถานะ + มูลค่า อยู่ในตารางรอบบิล · "อะไรค้าง" กับ "อะไรเพิ่งเกิด" อยู่ในสองการ์ดล่าง)
